## 【PART 1】 システム公式ルールブック（現場の業務要件）
※このセクションは美容室の現場の「魂」と「業務ルール」である。


### 0. アプリの目的と基本理念（魂）
- 魔法のような最適解: 予約は常に変動し、アシスタントの人数も休みの人数によって変わる。この常に変化するパズルに対して、最適解を魔法のように自動で解決する。
- 公平なバランス: 一人の負担が重くならないように、稼働時間（疲労度）などを考慮し、可能な限り公平なバランスで召喚する。
- お客様ファースト（不足ゼロ）の絶対原則: お客様を待たせないこと（未アサインによる人数不足を出さないこと）が最優先事項。足りないスタッフが出るのは絶対NGであるため、オーナーや優先トグルの優遇よりも、全体の不足補填（赤枠をなくすこと）を最優先とする。（練習や掃除などのフリータイムも、不足がない場合にのみ発生する）


### 1. 全体のアサイン処理フロー（順番）
召喚エンジンは以下の順番で計算を実行します。
1. 要件定義: 各予約のメニューから、必要な時間枠（スロット）と要求されるスキル・レベルを算出する。
2. 初回アサイン（最適配置）: 予約時間が早い順に、空いているアシスタントを条件（スキル等）に合致するスロットに割り当てる。（優先度の高いスタイリストはここでしっかりアシスタントを確保する）
3. 空きスタイリストの召喚（通常召喚＆特殊召喚）: 初回アサインで不足が出た箇所に対し、予約が入っていない空きスタイリストがいればヘルプとして割り当てる。また、アシスタントのお昼休憩を確保するための「特殊召喚」もここで発動する。
4. 破綻検知とマンセル発動: 上記を行ってもなお不足が出る場合、優先度の低いスタイリストから順にその場所を白紙に戻してマンセルを発動し、最低マンセル（圧縮状態）の組み直しを行う。
5. マンセル確定後の再計算: マンセルが確定した部分以外の「単独予約」の部分を、残ったアシスタント（およびスタイリストの特殊召喚）を使って白紙から再計算し、埋めていく。
6. 隙間ヘルプ・フリータイム（練習・掃除）の設定: 最終的に空いているアシスタントに、休憩、お昼、練習、掃除などの隙間業務を割り当てる。

#### 1-1. 複合メニュー結合時のスロット上書き原則
「カットカラー」などのベースメニューに対し、さらに「トリートメント」や「スパ」などの追加メニューが結合された場合、ベースメニューの持つアシスタントスロット（シャンプーや1液・2液などの薬液スロット）を置き換えます。
この際、全てのスロットを無条件で上書きしてはなりません（最初のプレシャンプー等が上書きされるのを防ぐため）。必ず、**時系列的に「一番最後の対象スロット」1箇所のみ**をトリートメントやスパに置き換える純粋関数ロジックを絶対のルールとします。


### 2. 通常アサインのルール（基本割り当て）
- スキル要件の絶対性: 各スロットに設定された「要求スキル」および「スキルレベル」を満たしていないスタッフは割り当ててはならない。
- 重複の回避: 同じアシスタントが同じ時間帯に複数のスロットを担当すること（兼任）は避ける。




#### 2-1. 掛け持ち状態でない場合（単独予約）の召喚優先度ロジック
予約が重なっている（掛け持ちしている）時間帯は必ずアシスタントを召喚します。予約が重なっていない（単独予約）時間帯については、以下のロジックで割り当てます。
1. オーナーの優遇: 重なっていなくても優先的にアシスタントを召喚する。ただし、これを優先した結果「必ずアシスタントが必要な場所」に配置できなくなる事態は避けること（全体最適化を優先）。
2. 他のスタイリストの優先順位: その日の「稼働率が高い人」から優先的に召喚していく。


#### 2-2. 単独予約における例外の挙動（優先度ダウンと召喚不要）
- 優先度ダウン①: 後ろに予約が入っておらず、1時間以上空いている場合、優先から外れる（最低優先度）。
- 優先度ダウン②: 後ろに予約が入っておらず、30分以上空いている場合、優先から外れる。（1時間以上空きよりは優先される）
- 召喚不要の原則: 前後に予約が30分以上入っていない（ぽつんとある）単独予約の場合は原則召喚不要。
  - 例外: 他のアシスタントの稼働率が赤色（高負荷）で、かつ該当スタイリストの稼働率が黄色以上（中〜高負荷）の場合は召喚する。
- 人員に余裕がある場合の絶対条件: 全体の稼働率が30％以上であり、かつアシスタントがその時間に2人以上余っている場合は必ずアシスタントを召喚する。


#### 2-3. 空きスタッフ選出時の優先度
1. 直前・直後のスロットを同じスタイリストで担当しているスタッフ（移動や交代の無駄を省くため）
2. 疲労度（稼働時間）が低いスタッフ
3. ランダムまたはリスト順


### 3. 空きスタイリストの召喚と「特殊召喚」
通常アサインでアシスタントが不足した場合、空いているスタイリストをヘルプとして割り当てます。この際、アシスタントの労働環境を守るための特殊召喚システムが発動します。
- 特殊召喚①（お昼交代）: 11:00以降。スタイリストがお昼済みであり、アシスタントがお昼未消化の場合。
- 特殊召喚②（休憩交代）: 16:00以降。スタイリストがお昼＋休憩済みであり、アシスタントがお昼または休憩未消化の場合。
※ UI上では「特殊召喚」という文字が表示される。

#### 3-2. スタイリストのヘルプ（召喚）時のUI描画と厳格な切り分け
アシスタントとしても登録されている兼任スタイリストは、手が空いていれば通常のアシスタント枠として他者のヘルプに回ることを許可する。UI上ではバッジに応じて以下の3つに厳格に切り分けて描画する。
1. 黄色（☆隙間ヘルプ / ☆名前）: アシスタント枠としての通常ヘルプ（バッジなし）。
2. 赤（召喚）: システムによる緊急呼び出し（sp_summon）。
3. 金（特殊召喚）: 究極の最終手段としての引き抜き（sp_special_summon_gap 等）。




### 4. マンセルシステムのルール（我慢と圧縮）
#### 4-1. マンセルの基本概念と目的
予約が重なる過酷な時間帯においてスタイリスト専属の「アシスタントチーム」を結成すること。マンセルは人数を確保するシステムではなく、最低限の人数構成（我慢のシステム）になるため、優先度の高いスタイリストには展開せず、普通のスタイリストに展開して人数を圧縮し、不足箇所にアシスタントを送るための仕組み。


#### 4-2. マンセル発動条件とスルー原則
- 未アサイン（不足）の発生: 通常アサイン等を行ってもなお赤枠になるスロットが存在する場合のみ、マンセル結成判定（レスキュー）を行う。
- 完璧なアサイン時のスルー原則: 予約が重なっていても、全てのタスクにアシスタントが完璧にアサインできている場合は、マンセルを発動させず通常アサインを維持する。


#### 4-3. マンセル結成のフェイルセーフ（予約の取りすぎ検知）
- マンセルは要求スキルを満たすスタッフがチーム内に確保できるかのみを厳格に判定する。スキルを持たずチームが結成できない場合はマンセル不成立となり、赤枠のまま弾き「物理的に予約を取りすぎている」という警告を出す。


#### 4-4. 処理の優先順位（我慢する順序）
優先度が低いスタイリストから順に適用されます。
1. 普通のスタイリスト（若手、ジュニアなど。限界まで圧縮する）
2. トップスタイリスト
3. オーナー（理想マンセルが組めるよう調整する）
4. 優先トグルONのスタイリスト（最後までマンセル化されない）


#### 4-5. チーム人数（最低マンセルと理想マンセル）
- 2列掛け持ち: 3マンセル（理想。スタ1+最高スキルアシ1+他アシ1） / 2マンセル（最低。スタ1+最高スキルアシ1）。これでも組めない場合は赤枠。
- 3列掛け持ち: 4マンセル（理想。スタ1+最高スキルアシ1+他アシ2） / 3マンセル（最低。スタ1+最高スキルアシ1+他アシ1）。2マンセルしか組めない場合は即座に赤枠。


#### 4-6. アシスタント獲得と引き抜き（強奪）のルール
【重要制約】高スキルスタッフの過剰配置（贅沢）の防止
必要スキルを満たすアシスタントが1人入れば、他のメンバーは可能な限りスキルレベルの低い（または持たない）アシスタントを選ぶこと。
- Step 1: 単独予約からの引き抜き
- Step 2: 他の理想マンセルからの引き抜き（お互いが最低マンセルで耐えられるか計算）
- Step 3: 余剰人員による理想マンセルへの昇格
- Step 4: 不成立（不足）の確定と、残りの再計算


#### 4-7. マンセルブロック内の自由配置と独立性
マンセルチーム結成後、そのブロックは独立した「閉じたチーム」となり、固定モードで自由に配置変更可能。これはマンセル外の再計算に一切影響を与えない。可能であれば常に解除を目指す。


#### 4-8. エンジンとUIの連携（ダミーID）
不足が発生しマンセル条件を満たした場合、エンジンは計算上空いているタスクにダミーID（MANCELL_STANDBY）をアサインしシステム上の赤枠エラーを消火する。UI側はこれを検知し「【チーム対応】」と描画する。


### 5. フリータイム（空き時間）の設定
お客様を待たせない人員確保が完全に保証された上で時間が余った場合：
1. 練習時間（30分）
2. 掃除
3. ペアでの練習・指導（スタイリストとアシスタントが同時に余った場合）
※ タイムライン上のブロッククリックで専用モーダルが表示され手動上書き可能。

### 6. ブロック（一時不在）の絶対優先原則
スタッフに設定された「ブロック（一時不在）」は、いかなるアサインよりも優先される絶対不可侵の制約である。
- **自身の予約との競合**: ブロック時間帯に該当スタイリスト自身の予約が入った場合でも、ブロックは解除・貫通されない。人員不足として「赤枠エラー（未アサイン）」となる。
- **特殊召喚の無効化**: サロン全体が回らなくなり「SP特殊召喚」の発動条件を満たした場合であっても、対象者がブロック中であれば貫通せず、緊急レスキューには向かわせない（そのまま赤枠エラーとする）。

## 【PART 2】 システムアーキテクチャ定義 (計算エンジンSSOT)
※このセクションは、上記PART1の現場ルールをプログラムとして実現するための絶対的なデータ構造と設計規約である。


### 1. 設計の基本制約
- 完全イミュータブル: 状態（`EngineState`）は完全に不変。各Stepは純粋関数。
- ループ（バックトラッキング）厳禁: 複雑な奪い合いは行わず、要求をTier（1:最低マンセル死守, 2:単独予約, 3:理想追加）に分け、一方向のトリアージで分配すること。


- UI状態の完全分離: アコーディオン展開（5分刻み表示）や自動スクロールなどの視覚的な状態管理は、計算エンジン（`EngineState`）には一切含めず、UI専用のモジュール（例: accordionManager）でローカル管理し、SSOTの純粋性を保護すること。


### 2. EngineState データ構造 (TypeScript型定義)
// ※これが計算エンジンの全入出力を司る絶対のデータ構造である
type SkillLevel = 1 | 2 | 3 | 4 | 5;
type StaffRank = 'owner' | 'top' | 'stylist' | 'junior';
type RequirementTier = 1 | 2 | 3; // 1:最低死守(掛け持ち), 2:単独予約, 3:理想追加
type AssignBadge = 'special_summon_lunch' | 'special_summon_break' | 'gambare' | 'sukima' | 'manual_fixed';


interface Staff { id: string; rank: StaffRank; skills: Record<string, SkillLevel>; priorityToggle: boolean; }
interface Menu { id: string; name: string; /* 要件定義用データ */ }
interface Reservation { id: string; stylistId: string; menuId: string; startTime: string; endTime: string; memo?: string; }
interface StaffTracker { totalAssignedSlots: number; hasLunch: boolean; hasBreak: boolean; }


interface Requirement {
  id: string;
  reservationId: string;
  stylistId: string; // 誰の予約か（優先度・マンセル判定で必須）
  requiredSkill: string;
  minSkillLevel: SkillLevel;
  tier: RequirementTier;
}


interface Assignment { requirementId: string; staffId: string; badges: AssignBadge[]; isLocked: boolean; }


interface TimeSlotState {
  time: string;
  stylistOverlapCounts: Record<string, number>; // スタイリストごとの掛け持ち列数
  requirements: Requirement[];
  assignments: Assignment[];
  unassignedReqs: Requirement[]; // 赤枠エラー
  freePoolStaffIds: string[];
  freeTimeTasks: Record<string, string>;
}


export interface EngineState {
  date: string;
  master: { staffs: Record<string, Staff>; menus: Record<string, Menu>; reservations: Reservation[]; }; 
  tracker: Record<string, StaffTracker>;
  timeSlots: Record<string, TimeSlotState>;
}


### 3. パイプライン・スケルトン
時間枠（30分）ごとに `reduce` で以下の純粋関数を順に実行する。
1. `defineRequirements`
2. `assignInitial`
3. `summonStylistAndSpecial`
4. `triggerMancell`
5. `recalculatePostMancell`
5.5. `gapAssignment` (隙間配置とSP特殊召喚スワップ)
5.6. `backwardSweepOptimization` (※全アサイン確定後、不足やハンドオフを検出し、メインアシスタントが空きであれば直接置換、他タスク実行中であればタスク開始Tickに遡ってチェーンスワップを実行する。その際、スワップ候補者の持つ gap_help 等の補助アサインは強制的に剥がして優先処理する最終最適化の純粋関数)
6. `assignFreeTime`










### 4. タイムライン・フリーズと再計算の境界ルール
予約変更や手動介入による「再計算（強制リセット）」が走った場合、時間軸（当日か未来日か）に応じて処理のスコープを厳格に分割する。
- 当日の再計算: 
  現在時刻を基準とし、過去および現在進行中の時間枠（スロット）は「確定済み（フリーズ状態）」として状態を完全に保持・ロックする。現在時刻より先の「未来のスロット」のみを強制リセット（白紙化）し、再計算を実行する。
- 未来日の再計算: 
  まだ時間が進行していないため、営業開始時刻からすべての時間枠を完全に白紙（ゼロ）の状態に戻し、全体最適の再計算を行う。
- 手動設定（フリータイム等）の扱い: 
  未来の時間帯に対して手動で設定されたフリータイム（練習・掃除など）は、全体の不足ゼロを最優先するため、再計算時に一旦強制リセットされる。
- 静的設定値の最新優先の原則（ブロック機能等）:
  過去の時間枠をフリーズして復元する際、各スタッフの疲労度（tracker等の動的状態）は過去実績を引き継ぐが、「不在ブロック設定」や「手動ピン留め指定」などの、計算の前提となる静的なユーザー設定値については、決して過去のキャッシュで上書きしてはならない。常にUI側から渡される最新の設定（options.blockedTimes等）を強制的に注入し、反映させること。
### 5. SOSモード拡張機能 (UI完全分離アーキテクチャ)
現場のスタイリストがアシスタント全員にヘルプを要請する「SOSモード」は、計算エンジン（SSOT）の完全性を保護するため、以下のアーキテクチャルールに則って実装しなければならない。
- エンジン非干渉の原則: SOSの要求データは `EngineState`（計算ロジック）には一切含めず、サモンロジックの判定に影響を与えてはならない。データはUI用の独立したStorage領域に保存・同期する。
- 独立コンポーネント化の徹底: 既存の緻密な多段レーン計算（mainView.js等）の崩壊を防ぐため、SOS機能は `sosManager.js` 等の独立したコンポーネントに完全に隔離する。予約ブロックのクリックイベント管理、ダイアログ生成、およびDOM（SOS帯）の生成はこのコンポーネント内で行い、メインの描画フローからはメソッドを呼び出すのみとする。
- UI描画と透過処理の仕様:
  1. 予約ブロック側: 該当する予約ブロックには「🆘」等のバッジを表示する。
2. アシスタントおよび全スタイリスト側 (全体ブロードキャスト): タイムライン領域上部に、SOSの時間範囲を示す「半透明の赤い帯」を描画し、その帯の上部に飛び出す形で「🚨 〇〇 SOS 9:00〜10:00」というテキストラベルを配置する。短い時間枠でも文字が潰れないよう、テキストは帯から独立して表示（overflow: visible, white-space: nowrap）させ、帯とテキストの合計高さを考慮して下部のブロック群を正確に押し下げる（オフセットする）こと。また、操作を妨げないよう赤い点線の「帯」部分のCSSには必ず pointer-events: none; を付与し、クリック判定を透過させること。ただし、一度設定したSOSを解除可能とするため、上部に飛び出している「テキストバッジ」部分にのみ pointer-events: auto; を付与してクリック判定を許可し、解除操作（確認ダイアログ等）を提供すること。


#### 5-5. 隙間ヘルプと玉突きスワップ（SP特殊召喚）の厳格な階層ルール
スタイリストが複数のお客様を掛け持ちし、アシスタントにタスク（シャンプーやカラー等）を任せている状態で、他所にどうしても埋まらない不足（赤枠エラー）が発生した場合、以下の段階的スワップ判定を実行する。


1. 第一段階：アシスタント放出の原則（通常スワップ）
スタイリストが直接他所のヘルプに向かうのではなく、まずは「スタイリスト自身が自タスク（カラー等）に代わりに入り、現在そのタスクを担当しているアシスタントを不足箇所へ放出（スワップ）する」ことを試みる。
条件を満たせば、放出されたアシスタントが不足箇所へ向かい、通常の「隙間ヘルプ」としてアサインされる。


2. 第二段階：スキル要件による放出ブロック
第一段階で放出予定のアシスタントが、不足箇所の「要求スキル（およびレベル）」を満たしていない場合、そのアシスタントをヘルプに回すことはできない（スワップ不成立）。


3. 第三段階：究極のSP特殊召喚（スタイリスト自身の直接レスキュー）
第二段階によりアシスタントの放出が不可能（スキル不足）であり、かつサロン全体で他にレスキュー可能なスタッフが誰もいない極限状況においてのみ、「SP特殊召喚」のトリガーが引かれる。
この場合、アシスタントはそのまま元のタスク（カラー等）に残し、スタイリスト自身が自顧客の管理を離れて不足箇所のレスキューに直接向かう。これは極めて例外的な緊急挙動として厳格に扱われる。
